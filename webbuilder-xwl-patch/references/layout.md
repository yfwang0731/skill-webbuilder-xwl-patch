# 布局：面板高度、列网格与工具栏

本文管**控件之间的关系与几何** —— 面板该给多高、列该给多宽、`x` 与 `labelWidth` 怎么摆、工具条挂在哪。
单控件的合法配置（某控件认哪些键、骨架长什么样）见 [`controls.md`](controls.md)；
值与字典怎么映射（`keyName` / `renderer` / 多选 / 值往返）见 [`value-mapping.md`](value-mapping.md)；
批量产出（脚本化生成、构造函数归一、双层闸）见 [`generation.md`](generation.md)。

> ⚠️ **本文的算法用来"新建 / 改版时算出该给多少"**，⛔ **不用来判定存量设得对不对**。
> 存量一律不动：存量的坐标与尺寸是人工调过的、也有**故意做窄 / 故意留白**的，
> 任何"按公式判存量"的做法都会制造大批误报。存量只给**提示级**（`note`）的观察，见 §二、§三各一条。

## 一、布局总则

**`absolute` 布局不会自增高。** 面板（`panel` / `form` / `module` 的可见区）用的是绝对定位：
子元素的 `x` / `y` / `width` / `height` 全部由**文件里的数字**决定，容器**不会**因为子元素放不下而长大。
由此推出三条：

- **高度必须算出来再写** —— 写小了子元素被裁（页面看起来"少一行"），写大了留一大块空白；
- **改一个子元素的 `y` 或 `height`，它下面所有元素都要跟着挪** —— 没有"自动重排"这一步；
- **同一行内的元素 `y` 相同，行与行之间靠 `y` 递增** —— 行距不统一就会出现"高低不齐"的锯齿。

**`x` 与 `width` 的口径**（最容易踩错的一条）：`x` 是**含 label 的整个控件的起点**，
输入框的左边缘在 `x + labelWidth`。所以同一区域内**对齐的是一组控件的 `x`**，
而不是"输入框的左边缘" —— 拿输入框边缘去对齐，`labelWidth` 不同的控件会横向错格。

## 二、面板高度：新建面板时该给多少

### 2.1 四步算法（⛔ 不是"行数 × 行距"的闭式公式）

1. **按 `y` 把子元素分组成行** —— `y` 相同的算同一行（同一行可以有多个元素）；
2. **行高 ＝ 该行 `max(height)`** —— 一行里有高有矮时取最高的那个，否则矮的会顶破该行；
3. **内容底边 ＝ 末行 `y` ＋ 末行行高**；
4. **默认面板高 ＝ 内容底边 ＋ 底部余量（8~12）＋（有 `title` 时再加 titlebar，26~38）**。

> ⛔ **不要**用 `26 + 10 + 行数 × 30 + 14` 这类把行距钉死的公式。实测两个面板：
> 一个高 **130** ＝ 内容底边 **92** ＋ **38**（行距 **30**、有 `title`）；
> 另一个高 **256** ＝ 内容底边 **200** ＋ **56**（行距 **28**、无 `title`）。
> ⇒ **行距 28 / 30 都出现过、开销 38 / 56 都出现过** —— 任何钉死行距的公式必然在另一半上算错。

### 2.2 四列对照表（算例：按 §2.1 的四步逐行算出，⛔ 不是实测存量）

| 场景 | 子元素 `y` 集合 | 内容底边 | 建议高度 |
|---|---|---|---|
| 单行条件条（无 `title`） | `{12}`，行高 28 | `12 + 28 = 40` | **50**（余量落在 8~12 的 **10**） |
| 两行表单（无 `title`） | `{12, 40}`，行距 28、行高 28 | `40 + 28 = 68` | **78**（余量 **10**） |
| 两行表单（有 `title`） | `{12, 40}`，行距 28、行高 28 | `40 + 28 = 68` | **108** ＝ 68 ＋ 余量 **10** ＋ titlebar 30 |
| 三行表格式表单（有 `title`） | `{12, 40, 68}`，行距 28、行高 28 | `68 + 28 = 96` | **136** ＝ 96 ＋ 余量 **10** ＋ titlebar 30 |

读表口径：**余量取 8~12 里的一段**（表里统一取 10）；`titlebar` 取 26~38 里的一段（表里取 30）。
余量给到上限（12）与给到下限（8）都在规范内 —— 要贴边给 8、要留白给 12，**别超出这个区间**。

### 2.3 存量面板一律不动，只给 `note`

**存量面板的 `height` 不改、不判、不反推。** 唯一允许的观察是一条 `note` 级提示：

> **`note` 判据**：`height < 内容底边 + 8` ⇒ 末行**可能被裁**。
> ⛔ 不进退出码、⛔ 不做等式、⛔ 不校验上界；`note` 只提示"可能裁行"，
> ⛔ **不反推"应该改成多少"** —— 存量是人工调的，反推出来的值会把有意的紧凑布局改坏。

## 三、列网格：`x` / `width` / `labelWidth`

同一区域（同一行、同一表单）里的控件按**列位**对齐，规则四条：

- **同一区域统一 `x`**：一列的开头 `x` 全相同；
- **`x` 是含 label 的整控件起点**，输入框左边缘 ＝ `x + labelWidth`（见 §一）；
- **一组连续控件占一个列位**：同一个列位内不再嵌套两套 `x`；
- **语义成对的控件必须同行相邻**：区间型的"起 / 至"两个控件放同一行、`x` 递增，
  ⛔ 不要分到两行去（分行的区间条件读起来像两个独立条件）。

### 3.1 列宽默认值（新建 `column` 时用）

**`width ≥ 标题显示宽 + 16`**，其中**标题显示宽 ＝ CJK 12px/字 ＋ ASCII 7px/字**。

例：标题 `规则名称` 是 4 个 CJK 字 ⇒ 4 × 12 ＝ 48，加 16 ⇒ **下限 64**。
实际给 **160**（偏宽但不截断）—— 下限只是"不能更窄"，不是"就该这么宽"。

> ⛔ **这些列不套公式**（新建时按惯例给，套公式会明显偏宽）：
> **序号**（`rownumber` / `index`）、**备注**（常配 `flex` 或故意留窄让用户拖）、
> **操作列**、**勾选列**、**状态标志位**（0/1）、**编码类**（固定位数）。
> 它们要么极窄、要么交给自适应。

### 3.2 存量列宽一律不动，只给 `note`

**存量的列宽不改、不判。** 同页里既有估宽明显大于实际宽度的列（例如估 144 却只给 **100**、
按上界会被截断），也**不能**据此判错 —— 存量是人工调的，也有**故意做窄**让用户自己拖的。

> **`note` 判据**：`标题显示宽 + 16 > width` ⇒ 标题**可能被截断**。
> ⛔ 不进退出码、⛔ 不判 `FAIL`、⛔ 不反推"该改成多少"，只提示"可能截断"。

## 四、`region` 拉伸：谁被撑满、谁固定

`region` 是**合法配置**（枚举 `center` / `north` / `south` / `east` / `west`），
可用 `xwl.py schema panel --controls <…/controls.json>` 复核该控件是否接受它。

判据只有一条：**`region:"center"` 会被撑满，`height` 随之失效。**

- 需要**固定高度**的区块 ⇒ 用 `north` / `south` ＋ `height`；
- 需要**吃掉剩余空间**的区块 ⇒ 用 `center`（典型是子表 `grid`）；
- ⇒ 一个容器里**只留一个 `center`**，其余全部 `north` / `south`；
  给 `center` 写 `height` 不会报错、但**不生效**（读文件的人会以为高度被控制住了）。

## 五、数字列右对齐

`column` 配 `"align": "right"`。适用与不适用**分得清**才不会滥用：

| 适用（数量 / 金额 / 比例） | 不适用 |
|---|---|
| 数量、件数、箱数 | 0/1 标志位（居中或左对齐更好读） |
| 金额、单价、合计 | 年份、月份这类"数字形态的标签" |
| 比例、百分比、换算系数 | 编码类（单号、料号、固定位数串） |

> ⚠️ 这一节是**项目口径 / 推荐**，**不是平台要求** —— 依据是注册表里 `column` 确实有
> `align [enum]` 这个键（合法配置），但"哪类列该右对齐"是**排版规范**，平台不强制。
> 因此它**不进任何自动判定**：`check` 不会因为某列没右对齐而报。

## 六、工具栏：两条硬规则

**推荐挂法**（通用做法，`itemId` 可自取）：

| 项 | 写法 |
|---|---|
| 建节点 | 在 `panel` / `module` 下建 `toolbar` 节点 |
| 挂到控件 | 目标控件配 `"tbar": "app.<toolbar 的 itemId>"` 或 `"bbar": "app.<toolbar 的 itemId>"` |

**硬规则一：`grid` 的子 `toolbar` 必须用默认命名 `tbar`。**

- **行为约束（实测 ＋ 多年经验，非孤例）**：写成别的名字，**前台不显示**。
- 机制（源码）：`toolbar` 的 `autoNames` 是 `{"grid": "tbar", "tree": "tbar"}`
  —— 设计器 `setNewNode` 时按父控件类型自动命名，`grid` 下的工具条因此固定叫 `tbar`。
  `autoNames` 的完整语义见 [`controls.md`](controls.md) 第四节（⛔ 本文不复制那张表）。

**硬规则二：一个 `grid` 只放一个 `toolbar`；要多个必须外置。**

- **行为约束（由规则一直接推出）**：同一层不能重名 ⇒ 第二个 `toolbar` 必然拿不到 `tbar`
  ⇒ **必然少显示**。
- 做法：第二个及以后的工具条**外置**成 `panel` / `module` 下的独立 `toolbar` 节点，
  再用 `tbar` / `bbar` 指向它（挂法见本节上表）。

> ⛔ 这两条是**约束**，不是可选项。写文档或写代码时**不要**加"未验证""据观察"这类限定词
> —— 它们会让人以为可以试试别的命名，而这条试错的代价是"页面上少一排按钮"且不报错。
