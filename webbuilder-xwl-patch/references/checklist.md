> 最容易跳过、后果最重的三条：
> ① 多行源**绝不能**压成一行（静默语义损坏，格式校验拦不住）—— 改完跑一次 `xwl.py diffguard`，
> 它是**唯一**能自动发现这种损坏的手段；
> ② 真跑 `patch` 必须带 `--backup`（或改动在 git 里可回退）；
> ③ 新建文件必须在**设计器里打开过一次** —— `check` 只证"格式能加载"，不证"页面能用"。

---

## 一、源形态与格式

- [ ] 用脚本/工具改的（**没有**用普通编辑器或 Edit 工具）
- [ ] **没有把多行源压成一行**（多行源压一行一律禁止）
- [ ] 若是单行源：只在一行形态上改，或已用 `expand` 转成设计器同款多行
- [ ] 改了换行符没有？（**全文件一致**即可，别手工改、别和 git 的 autocrlf 打架）
- [ ] 新增/修改的 JS 用的是**单引号**，字符串内没有裸 `"`

## 二、编辑方式与回退

- [ ] **默认走了结构级 `patch`**（只提供值/子树，格式由序列化器产出）；用了 `edit` 的话能说清为什么
- [ ] 若用了文本级 `edit`：锚点在文件里**唯一**（工具已强制）
- [ ] 真跑 `patch` 时带了 `--backup`（或改动在 git 里可回退）

## 三、验证

- [ ] `xwl.py check` 全绿（含 ④ 加载器等价解析、⑥ 事件 JS 语法）
      （④ 比对的是**加载器** org.json 的宽容面 —— 尾随逗号、`{` 之前的前导内容、**单引号键／未引号键／相邻贪婪 `{...}{...}`（只取第一个）** 都**不判 FAIL**；只保证"能加载"，**不等于**"符合 JSON 规范"；完整边界见 `references/faq.md` §一）
      （⑦ 的判定口径是**注册键** `normalName || itemId` —— 口径变更后既有文件可能新报 `[FAIL]`，属既有问题、不是本次改坏）
- [ ] 语义层面的改动已用 `git diff` 复核（格式校验查不出语义变化）
- [ ] 跑过 `xwl.py diffguard <file>`：没有「疑似把多行内容压平」的告警
      （主判据是**定义级**的：工作区某行 == 基线连续多行去掉续行符后拼接；只有它能自动发现这类损坏，`check` 查不出）
      ⚠️ 它**测不到**「压平的同时还改了内容（拼不出等式）、且增量不足以触发粗筛」那一档 —— 那类只能靠上一条的 `git diff` 人工复核

### 任务级独立验收：结构保护区与事件生命周期

本方法只验收**已给定对象**。开始前收齐四类输入：可追溯的任务开始基线、本次给定对象、对象内最小允许路径、触发该业务的明确条件。基线必须包含任务开始前已有的未提交编辑，不能直接拿 `HEAD` 代替；证据要区分原文层（字节、换行、未改区段）与对象层（解析后的键、值、数组身份），并写清这次结论覆盖哪些对象。

1. **结构比较**：先逐个验证最小允许路径确实发生了预期变化，再从两侧结构扣除这些最小允许路径，比较完整的剩余结构。数组发生位移时，先按稳定身份（如对象自身的 ID 字段）配对，再比较对应项；不能因为下标变化就误扣整列或整张 grid，也不能用错误下标配对。允许路径以外的键、值、层级或集合变化都进入差异。
2. **事件生命周期**：先从业务成功条件和动作位置写出预期动作，再覆盖业务成功、失败、取消和未发请求四条路径。确认成功路径只在该成功条件后执行应有动作，并在失败、取消或未发请求路径检出遗漏、早执行和错误动作。HTTP 成功码或框架字段名为 `success` 只表示技术调用状态，不能替代业务成功条件。
3. **完成状态**：每项复用现行 `通过 / 失败 / 未完成 / 不适用 / 未选择` 词汇；失败与未完成可以并存。缺任务开始基线、零对象、定位有歧义、必要覆盖缺失或运行证据不足时，整体结论不能写“通过”，但已有充分证据的局部项目可保留“通过”或“失败”。
4. **范围边界**：本方法不裁决关联验收展开一层还是递归，也不裁决验证调度或任务级完成证据如何生成；这些仍由上层的任务范围机制决定。

两组脱敏演练用于证明复核者会执行方法，不用于代表任何整项任务覆盖：

- **结构演练**：grid 中按列 ID 比较，editor 的最小允许标题变化应通过；相邻列宽变化、store 地址变化或数组位移后配错身份都必须被检出。
- **事件演练**：业务成功分支保存并刷新应通过；同一保存动作落在回调外，或业务失败分支执行保存，都必须被检出。
- **动态未知交接**：动作目标、事件入口或有效对象只有在运行时才确定，且没有可追溯运行证据时，记“未完成”并交接未知来源、基线、触发条件和已核实局部结论，不猜平台可达性。

## 四、改引用与控件结构

- [ ] 改的是**被引用的片段**时，已确认引用它的页面/入口能正常取到
- [ ] 改了引用（`store.url` / `Wb.request` / `Wb.open` / `Wb.upload` / `Wb.requestAg`）时：
      url 写的是**模块相对路径且不带 `.xwl`**，目标文件确实存在，参数名与下游一致
- [ ] 新增控件时：类型/父节点选对（`container` 才能挂真子控件；`grid` 的列/数据源是**配置载体**，
      见 [`controls.md`](controls.md)）
- [ ] 改 SQL 用的是 `@itemId` 寻址（而不是硬编码 `children[0].children[0]`）

## 五、SQL 与传参

- [ ] 改 SQL 文件时：`xwl.py sqlrefs` 通过（按**本文件内静态集合近似**核对 `{#名字#}` 与
      字面量 `request.setAttribute(…)`；该结果不证明执行、时序、分支或跨 module 生命周期，且 serverScript 里没写 `{#…#}`）
- [ ] 改 SQL 或查询页时：`xwl.py params` 无「SQL 需要但页面未发现来源」的告警
      （参数名 = 控件 `itemId`，对不上**静默失效**）
- [ ] 用 `out` 通路时：需要的参数控件**确实挂在该容器内**、`itemId` 没改过、
      类型是**取值控件**（button/label 之类没有 `getValue()`，不会被送）
- [ ] 没有在 `out` 与 `params` 里给**同名参数**写不同值
      （`store.load` 与 `Wb.request` 的覆盖方向相反）

## 六、itemId 命名

- [ ] `@itemId` 重名时**没有猜第一个**：用了 `@名字#N` 点名，或串联 `@` 段限定，
      或按父子关系确认过后再改
- [ ] 新增控件时**注册键 `normalName || itemId` 唯一**（列控件可重名 —— 列 `itemId` 默认 ＝ 字段名，**仅当同页存在多个网格**（字段名可能跨网格重复）时才加 `Col` 后缀（camelCase）；
      按钮 / 面板 / `tab` / 数据承载**必须**区分开）
- [ ] 若目标是"同一字段名出现在多处明细面板"：**优先补 `normalName`**（`app.<normalName>`），
      而不是改 `itemId` —— 补 `normalName` 是**新建键**，那条 `set` 要带 `"create": true`
- [ ] 改了 `itemId` 的话：**事件 JS 里对它的引用已同步改**，且 `itemids` 复查过
- [ ] `xwl.py check` 的 ⑦ 没有 `[FAIL]`（**未被引用的重名出 `benign`**、知道了就行 —— 老代码可留，新代码别再加）

## 七、新建文件时（额外必查）

- [ ] 用 `xwl.py new` 生成的（**没有**手写顶层键、**没有**拿别的文件当种子）
- [ ] 顶层 7 把钥匙齐全，且键序与 `SKILL.md` §1.3 一致
      （`new` 已保证；手写或 `--from-json` 时自查）
- [ ] `xwl.py folders <file>`：**已登记进所在目录的 `folder.json`**（否则设计器导航树里看不到）
- [ ] SQL 载体跑过 `sqlrefs`；引用 SQL 的页面跑过 `params`
- [ ] **在设计器里打开过一次**（`check` 只证"格式能加载"，不证"页面能用"；新文件也没有 diff 可比）
- [ ] 知道要让用户能打开还得在数据库 `WB_MENU` 挂菜单（范围外 —— 别以为文件建好就完事）
