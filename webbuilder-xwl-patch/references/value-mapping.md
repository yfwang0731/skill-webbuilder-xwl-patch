# 值映射：字典、`renderer`、多选与值往返

本文管**值与字典怎么映射**：一个字段该走 `keyName` 还是 `renderer`、多选下拉的三路来源、
存进库里的是什么形态、取出来怎么回填。
**语法写法**（`keyName` / `renderer` 各自怎么写、键名怎么拼）**只在** [`controls.md`](controls.md) 一处
—— 本文只给**判据与代价**，⛔ 不复制写法。布局与几何见 [`layout.md`](layout.md)；
批量产出见 [`generation.md`](generation.md)。

## 一、`keyName` 还是 `renderer`

**一句话判据：字典里有这个键 ⇒ `keyName`；没有字典 ⇒ `renderer`。**

| 数据从哪来 | 选哪个 | 为什么 |
|---|---|---|
| **代码表 / 字典表**（键 → 名称的固定对照） | `keyName` | 翻译由平台按字典做，页面不写代码；改字典不用改页面 |
| **业务枚举、多态值**（同一个字段在不同行代表不同含义） | `renderer`（`[js]`） | 没有统一对照表，只能按行判断 |
| 需要在单元格里**拼串 / 截断 / 加图标** | `renderer`（`[js]`） | 这是"渲染"，不是"翻译"，`keyName` 表达不了 |

- **`renderer` 多行同样合法** —— 单行只是便于生成与 diff，⛔ **不是平台限制**。
  本仓外参考页实测：有把整个 `switch` 写成多行的 `renderer`，页面正常。
- ⛔ **别反过来**把"必须单行"当平台约束写进交付文档 —— 那会让接手的人为了"守规矩"去压行，
  而压行恰恰是本仓最反对的形态（多行被压平是不可逆的语义损坏，见 [`faq.md`](faq.md) §三）。

## 二、⛔ 不在 SQL 里写 `CASE WHEN` 翻译

**做法**：翻译留在**页面层**（`keyName` 或 `renderer`），SQL 只出**原始值**。

- ⚠️ 这是**推荐做法**，**不是平台限制** —— 在 SQL 里写 `CASE WHEN` 平台照样执行。
- 理由只有一条但很硬：**翻译规则会被复制到每一个用到该字段的 SQL 里**，
  字典一变就要满工程找 `CASE WHEN` 改；而页面层的 `keyName` 只改字典一处。
- **反模式与替代**：反模式 ＝ 查询 SQL 里 `CASE WHEN status WHEN '1' THEN '待审批' …`；
  替代 ＝ SQL 出 `status` 原值 ＋ 页面列配 `keyName`（无字典则配 `renderer`）。

## 三、多选下拉的三路来源

多选下拉（`multiSelect:"true"`）的候选项有三种来源，**按数据在哪选**，别混：

| 路 | 数据在哪 | 怎么搭 | 适用 |
|---|---|---|---|
| **A 字典型** | 代码表 | `combo` ＋ `keyName` ＋ `multiSelect:"true"` | 候选项就是字典的键，翻译也由字典做 |
| **B 内联型** | 页面文件里 | `pickList` 写**二维数组的字符串**（值 / 显示两列） | 候选项少、且与业务无关（几个固定选项） |
| **C 取数型** | 另一个 `store` | 子 `store` ＋ `valueField` / `displayField` | 候选项来自库（另一张表、另一段 SQL） |

⚠️ **`keyName` ＋ 子 `store` 混写**：**未验证、建议避免**。两者都在"提供候选项与显示名"，
职责重叠但走的是不同机制 ⇒ 可能出现候选重复或显示名不生效。
**验证方法**（真要这么写，先在设计器里验一次再落文件）：
① 打开页面看下拉里是否出现**两套候选**（字典一套 ＋ store 一套）；
② 选中并保存，再打开看**回填的是显示名还是原始值**；
③ 把其中一路去掉再对比一次 —— 两次结果一致才说明其中一路是无效配置。

## 四、值往返：写进去什么、取出来是什么

### 4.1 三条硬事实

1. **`Wb.getValue(容器)` 对多选 combo 原样返回数组** —— ⛔ 不自动序列化。
   ⇒ 直接塞进 SQL 参数会变成数组的字面形态，必须自己决定怎么存（见 §4.2）。
2. **回填用 `setValue(Wb.decode(...))`** —— 存进去是什么形态，取出来先解成数组再回填，
   ⛔ 不要直接把库里的字符串塞给 `setValue`（多选控件拿到的会是"一个元素"）。
3. **`Wb.decode` 是严格 JSON** ⇒ **库里必须存 JSON 文本**（如 `["1","2","3"]`）。
   存成逗号文本再 `Wb.decode` 会抛异常，而异常在回填路径上常被**吞成空数组**（表现为"值丢了、还不报错"）。

### 4.2 存储格式的代价（两种都能用，代价不同）

| 存法 | 字符数（同 3 个值） | 谁能直接读 | 代价 |
|---|---|---|---|
| **JSON 文本** `["1","2","3"]` | **13** | 全平台一致（凡用 `Wb.decode` 的地方都能读） | 占空间；**列宽要 ≥20**，否则显示被截断 |
| **逗号文本** `1,2,3` | **5** | 只有**约定好这一列格式**的页面能读 | 省空间；但这是**该列的私有约定**，别的页面用 `Wb.decode` 读会抛异常、被吞成空数组 |

选逗号文本的**附加义务**（缺一不可）：
① 读取处必须写**容错解析**（先试 JSON、失败再按逗号切）；
② **在列注释 / 交付文档里声明该列格式** —— 否则下一个接手的人按 JSON 读，值会静默变空。

### 4.3 列宽自检（存之前先量一次）

存 JSON 文本前先量该列现有最长值：`max(char_length(<列>))` 与
`information_schema` 里的 `character_maximum_length` 对一下 ——
**列宽 < 最长值**时插入会被截断或报错，而这类失败常在"保存"这一步才暴露。
列宽下限按 §4.2 取（JSON 文本 **≥20**）。

## 五、`keyName` 的缓存提醒

`keyName` 走**代码表缓存**：改了字典里的 `s_code`（名称）之后，**不刷缓存可能仍显示旧名**。

- ⚠️ **这是外部事实**（不在本仓范围内，本仓没有代码表缓存的实现也没有复现手段）：
  **来源 ＝ 使用者的现场经验陈述**；**时点 ＝ 本次交付**。
  ⛔ 不要把它写成"平台保证会刷新"或"必现"—— 它是"可能"，观察到的现象是"改了名页面上还是旧的"。
- **可操作结论**：改完字典名之后，**先刷缓存再验页面**；若页面已显示新名，不必再查别的。
