## 一、格式与解析

格式 / 编码 / 加载相关：出问题先看这一组。

**Q：`check` 报了 `[FAIL]`，怎么排查？**
A：先看是第几项。①–⑤ 是**格式**层面（文件坏了）、⑥ 是**事件 JS 语法**，⑦ 是**命名质量**（文件能用但取值有风险）。
①–⑥ 有 FAIL 时用 `<file>.bak` 回退再逐项对照；⑦ 的 FAIL 单独跑 `check` 或 `itemids` 看候选清单。

九项分别查什么（8 项判定 ＋ 1 项只提示；**另**：给了 `--controls` 时另校 `configs` 键与内联 `[js]`、不计入这九项）：

| # | 检查 | 判定 |
|---|---|---|
| ① | 无 BOM | 文件不以 `EF BB BF` 开头。**这是仓库规范 + 工具限制**：框架从 `{` 处截取、BOM 落在它之前会被丢掉，所以带 BOM 的文件**能**加载（设计器保存后 BOM 也会消失）；工具则直接 rc=2 |
| ② | **换行一致（不混用）** | 加载器 LF / CRLF / CR 都收，只有「同一文件里混用」才判失败；**单独的裸 CR（纯 CR 文件）不算格式错，降为 `[warn]`**（设计器 / 仓库从不产出这种形态，改动它会整份 diff） |
| ③ | 无「反斜杠 + 空白」行 | 任何行都不以 `\` + 空格/Tab 结尾 |
| ④ | **加载器等价解析** | 归一化后按加载器规则解析通过（**④ 通过 ⇒ 框架能加载它**；**反向不成立** —— 框架比 ④ 更宽）；**现接受尾随逗号**（如 `{"a":1,}`），`{` 之前的前导内容也直接丢弃、不算错 |
| ⑤ | 末行结构 | 末行不以 `\` 结尾（首行之上的续行由 ③ 管） |
| ⑥ | 事件 JS 语法 | 抽出所有 `events.*` 的 JS 值 → `node --check` |
| ⑦ | **注册键重名分级** | **只有「按注册键（`normalName` 优先、回退 `itemId`）重名 且 已被事件 JS 引用」判 FAIL**；未被引用的重名出 `benign`，不影响结论 |
| ⑧ | **加载链完整性**（**只提示、不进 rc**） | 对齐框架取键方式：`children` 须是**非空数组**、`children[0].configs` 与 `roles` 须是**对象** —— 否则页面在**加载期**抛（文件能被 ④ 解析、页面却打不开）。全过 ⇒ `[note] ⑧ 加载链完整性：无异常`；有违规 ⇒ `[warn] ⑧ 加载链完整性：…`；④ 解析失败 ⇒ `[note] ⑧ 加载链完整性：因解析失败跳过`。**另含「数据加载链」一条**（**仍属 ⑧**）：页内有 `store` 节点、且**页内所有 store 都没有** `configs.autoLoad`（`true`／`"true"`／`"1"` —— ⚠️ **页级判据**：任一个 store 有 `autoLoad` 即整页放行）、页内**承载 JS 的字符串**（`events.*` 的值 ＋ `configs` 的字符串值，逐段剥注释后）也扫不到 `.load(`／`store.reload(` ⇒ 报 `[warn]`。⚠️ 本条是**负向断言**（「结果表**永不**加载」）：**窗口内嵌／窗口以子页方式打开**（由父页 load）、**运行时动态绑定**时**不适用**，须结合**源页语义**与**引入方式**人工确认；⛔ 只 `warn`、**不进 `rc`**。⚠️ 与验收侧同名指标的**口径差异**：那边按**文件名**认页（`*.page.xwl`），`check` 面对**任意** `.xwl` ⇒ 这里改按**内容级**（页内出现 `type == "store"` 即查）—— 照搬文件名判据，本项在非 `*.page.xwl` 上几乎永不触发。 |
| ⑩ | **`configs` 值类型** | 逐个节点看 `configs` 的**每一个值**：**只要有一个不是字符串就判 FAIL**（键不论、值不看语义）。判据来源是"加载器按 String 取值"——`300` 这类数字、`true` 这类裸布尔都可能让页面在取值处崩。⚠️ **只判类型、不判语义**：`"300px"` 仍是字符串 ⇒ **不报**（判语义会把注释、表达式一并误杀）。可用 `--no-cfgtype` 关闭本项。⚠️ 用 `--controls` 也不改本项结论（类型判据与注册表无关）。**通过态留行**（否则分不清"跑了且干净"与"根本没跑"）：全为字符串 ⇒ `[ok]   ⑩ configs 值类型：<N> 个节点、0 个非字符串值`（`[ok]` 后是 **3 个空格**，`<N>` ＝ 实际扫过的 `configs` 对象节点数）；`--no-cfgtype` ⇒ `[note] ⑩ configs 值类型：已按 \`--no-cfgtype\` 跳过`。 |

> **关于 ⑨（不在上表、也不计入九项）**：⑨ 校的是 **`configs` 键合法性**（某控件认不认这个键），
> 判据来源是设计器控件注册表，因此**只在显式给 `--controls` 时跑、只打 `[warn]`、不进 `rc`**
> （未收录的既有键在存量里很常见，判 FAIL 会开开关即一片红）。
> ⚠️ 另一件事**要分清**：**取不到注册表 ⇒ `rc=2`** —— 这属**调用方配置错**（路径不存在 / 读不了 / 不是可解析的 JSON，
> 含「是 JSON 但里面一个控件 type 都没有」的 `{}` / `[]` / `{"foo":1}`），**不是被检文件的内容缺陷**，
> 所以它既不算失败项、也不判文件的对错；但**不整条拒跑**：`①–⑧⑩` 仍**照常判定**、每个文件的结论照打，
> 只是 ⑨ 与 `configs` 内联 `[js]` 未校；全部文件跑完后打一行
> `[note] --controls 取不到控件注册表: <路径>（…）` 说明原因，再给 `rc=2`。

**自己写校验脚本时别踩两个坑**：② 别写成"必须 CRLF"（设计器**写在服务器上**，
产物换行 = 那台服务器的 `line.separator`，Linux 上就是 **LF**；
那样会把合法文件判失败）；④ 是把「反斜杠 + 换行」替换成「**反斜杠 + 字母 n**」两个字符
（`re.sub(r'\\(?:\r\n|\r|\n)', r'\\n', text)`，再对 `text[text.index('{'):]` 做 `json.loads`），
**不是替换成换行符** —— 写错会误报。另 ④ **接受尾随逗号**（加载器 org.json 如此，如 `{"a":1,}`）：
归一化时**只在字符串外**删它，字符串内的逗号不能动。

> `patch` / `edit` / `expand` **写盘后的自动校验只判 ①–⑥** —— ⑦ 是命名质量而非格式，
> 全判会导致"写盘成功却返回非 0"。
> 正文流程见 [`SKILL.md`](../SKILL.md) 第三章。

### check 的校验面：校什么、不校什么

`check` 说的是「**文件格式没坏 ＋ 事件 JS 语法通 ＋ 注册键不打架**」，**不证页面可用**。它**默认不做**「控件选型与键名合法性」这一整层：**给了 `--controls` 时会校 `configs` 键合法性 ＋ `configs` 内联 `[js]` 语法**；不给时合法性与逐键核验只能靠外挂 `schema --controls`。

**① 校什么（逐项）**：就是本文上面那张九项表 —— ①–⑤ 格式与结构、⑥ 事件 JS 语法、⑦ 注册键重名分级、⑩ `configs` 值类型、⑧ 加载链完整性（**只提示、不进 rc**）。逐项判据见那张表，此处不重复。**另**：给了 `--controls` 时**另校 `configs` 键与内联 `[js]`**（缺省不校、也不自动找），**不计入上表**。

**② 明确「默认不校」什么**（口径来源：本轮实例测试的注入试验；其中 `configs` 键合法性 / 内联 `[js]` 两行在**给了 `--controls`** 时会校）：

| 不校的事 | 表现 |
|---|---|
| `type` 是否在注册表内 | 改成注册表里没有的 `type` 仍 `ALL OK`（`schema` 才会拒） |
| `configs` 键是否合法 | 给控件加它不认的键仍 `ALL OK`（**给了 `--controls` 会 `[warn]` 指出**，但不进 rc） |
| `configs` 里标 `[js]` 的键（`renderer` / `validator` / `handler` …）的**语法** | 坏 `renderer` 静默过检（⑥ 只校 `events.*`；**给了 `--controls` 则判 FAIL**） |
| 引用是否可达 | 不解析引用 |
| 取数链路（`store.url` 指向不存在的文件） | ⭐ **已收紧**：`--strict` 下**判失败（`rc=1`）**（不给 `--strict` 仍只告警、`rc` **不变**）；显式占位（`<…>`／`…`）只 `[note]`、**永不判红**；`__MODULE__` **分两段判**：能被解析成**真实目录**（页面所在模块目录）时与普通 `m?xwl=` 同口径 —— 目标文件不存在就 `[warn]`、`--strict` 下 `rc=1`；解析不到（没给 `--module-root`／根不像模块根／页不在根下）才按显式占位 `[note]` 并**写明原因**。⚠️ 若 `__MODULE__` **之后的段本身**是显式占位（`<…>`／`…`）⇒ 按占位 `[note]`、**不判悬空**（与"整键是占位"同口径）。⚠️ **能力边界**：`__MODULE__` 在多数执行上下文下由框架运行期替换、不指向真文件 ⇒ 工具只在「能解析到真实目录」时才敢判悬空，其余一律 `[note]`（豁免宁可宽、避免把用 `__MODULE__` 作**真实目录名**的页面大规模误判）⇒ 那类工程里真悬空**不出 `[warn]`** |
| 页面能不能用 | 真冒烟要在设计器里打开 |

**③ 注册表怎么发现**：⑦ 的注册键分级靠「**向上找 `wb/system/controls.json`**」自动发现注册表；**找不到时静默回退内置兜底**（不报错）⇒ 同一个文件，放进工程 `wb/` 树里跑会显示注册表路径、放在工程外跑会显示「未找到」。**`configs` 键合法性 / 内联 `[js]` 语法**这两项**另走 `--controls`**：`check` **现支持 `--controls`**（**给了才校；缺省不校、也不自动找**）。

**④ 适用版本**：本清单描述**当前发布版**的校验面，精确版本号以 [`CHANGELOG.md`](../CHANGELOG.md) 顶部为准。`configs` 键校验、`configs` 里 `[js]` 键的语法校验**已随 `check --controls` 落地**：它们**只在显式给 `--controls` 时跑**（缺省不校、也不自动找）⇒ **除新增的 ⑩ 外**，不给开关时本清单的校验面逐字节不变。这也正是 `SKILL.md` 只留一句「不随时间变」的稳定声明、**不逐条列本清单**的原因 —— 逐条列会被下一条 minor 线推翻。

**Q：页面白屏 / 加载报解析错误？**
A：先 `check` 看 ④（加载器等价解析）。常见外因是改的时候**写成了裸 LF** ——
普通编辑器与通用文本替换工具都会造成这个，必须走 `patch`（文本级 `edit` 也要保留原换行）。
详见本文 §一（磁盘形态与硬规则）。

**Q：工具报「不是 UTF-8 文本」，文件在编辑器里看着好好的？**
A：文件被存成了别的编码（中文 Windows 上最常见的是 **GBK / ANSI**，其次是 **UTF-16**，
即"另存为"时选错了编码）。报错形如：

```text
[FAIL] 不是 UTF-8 文本（xwl 必须是无 BOM 的 UTF-8）：'utf-8' codec can't decode byte 0xb3 in position 236
```

**修法**：用编辑器**另存为 UTF-8（无 BOM）**；或在 Git Bash / WSL 里转一次再覆盖：

```bash
iconv -f gbk -t utf-8 page.xwl > page.utf8.xwl && mv page.utf8.xwl page.xwl   # 先 diff 确认内容没乱
```

**为什么工具不替你猜编码**：猜错会把中文写成乱码，而**乱码文件本身是合法 UTF-8** ——
`check` 会一路放行，等于把损坏藏进仓库。所以这里宁可停在门口（这条报错是**有意的**）。
注意退出码：`check` 有 `[FAIL]` 给 `1`；**`--controls` 取不到控件注册表给 `2`**（属调用方配置错 —— 此时 `①–⑧⑩` 已照常判定、只有 ⑨ 与 `configs` 内联 `[js]` 未校）；其余子命令的**前置条件不满足**给 `2`，见 [`SKILL.md`](../SKILL.md) §4.2。

**Q：为什么用严格 JSON 解析判「能不能加载」会误判？**
A：加载器是 **org.json**，它比标准 JSON 宽容：字符串里的裸控制字符（未转义的换行 / Tab）照收、
**对象与数组的尾随逗号**（如 `{"a":1,}` / `[1,2,]`）也接受、`{` 之前的前导内容直接丢弃。
Python 的 `json` 会报 `Invalid control character` / `Illegal trailing comma`。
本工具用 `json.loads(..., strict=False)` 对齐裸控制字符、并用**字符串感知**地删尾随逗号对齐后者。

多行源的**磁盘形态**（续行符是单个 `\`、紧邻换行；值里的 `"` 写成 `\"`）：

```text
{ ... "click": "var rec = app.headGrid.getSelection()[0];\
if (!rec) {\
  Wb.info('请选择一条记录！');\
  return;\
}" ... }
```

> **原理**：加载器先把「反斜杠 + 换行」换回 JSON 的 `\n` 转义，再按 JSON 解析 ——
> 所以磁盘形态与运行时形态不是一回事。另外**加载器是 org.json、比标准 JSON 宽容**
> （字符串里的裸控制字符照收、**尾随逗号也接受**）⇒ 判"能不能加载"**别用严格 JSON 解析器**下结论。

**Q：`check ④` 报解析失败，但这个页面在系统里能正常打开？**
A：④ 只对齐了加载器（org.json）的**部分**宽容面 —— 目前处理**尾随逗号**、**字符串内裸控制字符**，`{` 之前的前导内容也按加载器规则丢弃。**org.json 另还接受这 4 类**：**单引号键**、**未引号键**、**未引号值**、**相邻的贪婪 `{...}{...}`（只取第一个）** —— 加载器**接受**它们、工具**现已对齐** ⇒ **这 4 类不再报 ④ FAIL** —— ⚠️ **但有一处例外**：文件若**在第一个 `{` 之前还有前导内容、且该前导里含未配对的引号**（例如行注释里出现一个撇号），归一化会被这个引号带偏 ⇒ **仍报 ④ FAIL**（加载器本身接受）；属**已知能力边界**，遇到时先删掉前导里的引号再校验。⚠️ **现在只剩 1 个未对齐面**（加载器接受、工具仍报 ④ FAIL）：**键名含 `-` 的未加引号键**（如 `{ a-b: 1 }`）—— 属**已知能力边界**（当前语料实测零实例）；遇到时给**键**补上双引号即可。（**未加引号的「值」**如 `{ a: abc }` 已对齐 ⇒ 不再报 ④ FAIL。）⚠️ **哪些命令吃这套宽容面**（三条**只读**命令共用同一份实现，不会再各说一套）：
> · **接受**（单引号键／未引号键／未引号值／相邻 `{...}{...}`）：`check` 的 ④、`params`、`dump`、**`edit`**（`edit` 是**文本级**替换、不重建文件 ⇒ 这类写法**可以直接改**、也不会被重排）；
> · **能识别但拒写**（`rc=2`、目标文件**一个字节都不动**）：`patch`／`expand` —— 它们是**整份重建**（解析 → 按设计器算法重排 → 写回），对这些写法写回等于**顺带把格式全改了**，`git diff` 会被格式变更淹掉、真正的改动反而看不见 ⇒ 拒写并点明「命中的是哪几类」；出路两条：用 `xwl.py edit`，或先手工把键／值补上双引号再 `patch`/`expand`；
> · **仍走 strict 入口**（这批**没**扩过去）：`sql`／`events`／`sqlrefs`／`itemids`／`paths` —— 遇到上述写法仍报「无法按加载器规则解析」；
> · 无论哪条命令：**键名含 `-` 的未加引号键**仍判 ④ FAIL（见上一条能力边界）。⭐ **但性质是「口径对齐」、不是「消除现存误报」**：全语料 8 个 wb 根 **25 077 页**（剪枝口径）**零实例** ⇒ **本次未撤销任何现存报错** —— 改的是「**将来**遇到这类文件时的判定」，避免**将来**误判。而 **`\x` 非标准转义**加载器**同样拒绝** ⇒ 工具报 ④ FAIL 是**正确的**、**维持报错**。（口径：**①–④ 四类宽容面全已对齐** —— 序号同前一句；**仍报错的只有**「键名含 `-` 的未加引号键」这一条能力边界，另有前导内容含未配对引号那一处例外。经 Java 实机取证：官方多版本与**工程实际使用的那一个 jar** 结论一致。）⚠️ 无论哪类**都不是合法 JSON、设计器不会产出**，**遇到建议改掉**；**但 ④ 报错未必等于文件损坏，别只凭它下结论**。

## 二、命名与引用

取值取错人、改了参数没生效 —— 都是「名字对不上」。

**Q：事件 JS 里 `app.X` 取不到值，或者取到了别的控件？**
A：**注册键重名**。框架用**注册键**注册、注销时按同名键 `delete`
—— 所以**任一重复项被销毁会把整个名字删掉**。处置时**先读父子关系判断哪个才是真目标**，
再把候选清单交给用户选，不要"删一个"或"挑一个"。详见 [`SKILL.md`](../SKILL.md) 第七章。

> 名字含中文 / 空格 / `.` 等**非合法 JS 标识符**时，点号访问不适用，只能用 `app.get('名')`
> **或** `app['名']` 取（`configs.id` 那套命名空间不在本工具建模范围）。

**Q：`params` 报"SQL 需要但页面未发现来源"，可那些参数明明是调用方页面传进来的？**
A：**这是能力边界，不是 bug**。`xwl.py params <页面>` 只判你给的这**一个页面**静态可见的来源；
`Wb.open({url:'m?xwl=…', params:{…}})` 传进**子页面**的键写在**调用方**页面里，子页面自己看不到
（运行时值从 request 取，静态不可见）。⇒ 要核对这条链有**两条路**：**①** 到**调用方页面**跑 `params`（看它往子页面传了什么）；**②** **就在本页**跑 `params --upstream`（**默认关**）—— 它在 `--module-root` 内**单根全扫**，列出**本页的上游调用方与传入键**，并给一行载入侧汇总。
⚠️ ②的三个边界要说清：**只认 `params: {名:值}` 字面量键**（`out: app.<容器>` 与运行时拼接的 url **只计数**）、**只扫单根**（**跨工程的调用方找不到** —— 那是口径、不是缺陷）、**不改退出码**。
见 [`SKILL.md`](../SKILL.md) §5.4 与 §六。

**Q：改了 SQL 里的参数，但页面查询结果不对？**
A：参数名 = 控件 `itemId`，**对不上是静默失效的，不报错**。跑 `xwl.py params` 看
「SQL 需要但页面未发现来源」的告警。两条通路（`out` / `params`）的规则见
[`SKILL.md`](../SKILL.md) 第五章与 [`sql-fragments.md`](sql-fragments.md)。

**Q：同一个文件，在两个不同目录下跑，为什么结论不一样？**
A：工具按**单 webapp（单个 wb 根）**判定 —— 引用解析、注册表、`sqlrefs` 的"缺没缺"**只在本根内找**。
多模块工程实测是**各自独立部署**（`target/` 展开产物只含一个模块的 xwl；动态模块 jar 里没有 `wb/`），
所以"在另一个 webapp 里找得到"**不等于**"本根可用"。⇒ 要核对跨 webapp / 跨工程的引用，
**到目标工程（目标 wb 根）里跑**。见 [`SKILL.md`](../SKILL.md) §5.2。`--upstream` **同样只扫单根**（`--module-root` 内），所以**跨 webapp ／ 跨工程的调用方它找不到** —— 与上面"单根语义"是同一个口径。

**Q：页面能打开、不报错，但列表就是一条数据都没有？**
A：先查 `store` 的 `url` 有没有写**漏** `m?xwl=`。写成裸路径（或只写文件名）时**页面不报错、数据就是不加载** ——
因为框架根本不认为那是一个 xwl 引用，`store` 拿不到数据源，而"没有数据"本身不是错误。
- **正确写法**：`url` 写成 `m?xwl=<模块相对路径，不带 .xwl 后缀>`（见 [`SKILL.md`](../SKILL.md) §5.2）。
- **怎么确认**：`xwl.py paths <file>` 列出 `url` 字段位置，`xwl.py params <file>` 会核这条链；
  若 `url` 里没有 `m?xwl=`，这两步都能看出来。
- **反模式与替代**：反模式 ＝ 把 `url` 写成 `xxxSql/queryXxx`（看着像路径，框架不当引用处理）；
  替代 ＝ 补成 `m?xwl=xxxSql/queryXxx`，再用 `sqlrefs` / `params` 复核目标文件确实存在。

## 三、能不能这么改

动手前的判定：这条路能不能走、走完怎么确认没改坏。

**Q：能把 `.xwl` 压成一行吗？**
A：**多行源一律禁止**，而且这条**没有格式校验能拦住**。把「反斜杠 + 换行」直接删掉
（而不是替换成 `\n`）之后文件**依然是合法 JSON**，`node --check` 还可能因为"只剩一句注释"而返回 0，
`check` 也照样全绿（压平后文件自身是自洽的）—— 判据只能是**相对基线**：
`xwl.py diffguard <file>`（这是唯一能自动发现它的手段），或人工 `git diff`。

`diffguard` 的主判据是**定义级**的：*工作区某条物理行 == 基线里连续 ≥2 行各自去掉续行符后拼接的结果*
（这正是"压平"的定义），所以"合法删掉一段多行 JS"与"单行改长"都不会误报；
**「精确命中」还要满足前置必要条件 —— 续行符数或行数减少**（计数没变就不可能是压平），
否则只给 `[note]`（文案写明「内容移动/复制，不是压平」，**不计入告警**）。输出还会指明**基线的哪几行被并成了工作区的哪一行**。
默认只告警，`--strict` 才阻塞。
**这一档它也测得到**：压平**同时**还改了内容（拼不出等式）、且增量又不足以触发粗筛判据 ——
这种组合现在由**第三条判据（相似度档）**兜住：只在「续行符数或行数至少有一个减少」（＝压平的定义）时启用，
把基线里**连续 ≥2 行**去掉续行符后的拼接与工作区该行比相似度，达到阈值即判疑似；
⛔ **单行对单行不算**（那只是「改了内容」，不是压平）；逐字相等的仍走精确判据、不重复报。
**短行同样在射程内**：长度只用来省算力、**不是判据** —— 两三行短内容并成一行（合并后照样很短）也判得到；
代价是"只看行长"挡不住的误报由**逐行覆盖度**兜住（窗口里每一行的内容都得真进到那一行里去）。
默认只告警、`--strict` 才阻塞（与精确判据同级）。

**另外一处会主动提醒你的是 `edit`**：它手上有 old / new 两端，会 `[warn]` 报出续行符少了几个；
但用编辑器 / 通用替换工具改的它看不到。单行源能不能保持一行、多行源为什么不能压，
见 [`SKILL.md`](../SKILL.md) 2.2 与 2.3。

**Q：能用文本替换批量改一批文件吗？**
A：**不要**。工具对 `edit` 强制断言锚点唯一、不唯一就中止 —— 这是防呆不是障碍：
全文相同的 `select`、相同按钮文案都很常见，盲替换会把不该动的地方一起改掉。
锚点不唯一时把上下文扩到足够，别用 `--expect N` 绕过；改多个文件就一个个走 `patch`。

**Q：怎么确认这次改动没改坏？**
A：三层缺一不可 —— ① `check` 全绿（证明**格式能加载**）；
② `git diff` 复核（格式校验**查不出语义变化**，见 [`SKILL.md`](../SKILL.md) 2.3）
—— 其中"多行被压平"这一档可以交给 `xwl.py diffguard <file-or-dir>` 自动判
（主判据是**定义级**的：工作区某行 == 基线连续多行去掉续行符后拼接；默认只告警，`--strict` 才阻塞）；
③ 涉及 SQL / 传参时把抽取出的 SQL 灌真实库跑一遍（或交叉核对 `sqlrefs` / `params`）。
逐条版本见 [`checklist.md`](checklist.md)。

另外，**`patch` 中途报错一律拒绝写盘、不会留下坏文件** —— 出错后目标**文件没被动过**；
按提示用 `paths` / `dump` 核对后改 `path`，**别猜**；`@itemId` 重名时它给候选清单让你选，
而不是替你挑一个。

**Q：子表一行都没有，代码写了 `addEdit` 循环，但既不报错也不出数据？**
A：多半是这份 `store` **从来没有 `load` 过**。在**从未 `load` 过**的 store 上调
`addEdit` / `insert` / `loadData` / `removeAll` 会**静默无效、连 JS 报错都没有** ——
看起来像"代码没执行"，其实是执行了但落在空壳 store 上。
- **可行写法**：先 `store.load({params: {…}, callback: function () { …addEdit… }})`，
  ⚠️ **添加必须写在 `callback` 里** —— `load` 是异步的，写在 `load` 后面那一行时数据还没回来。
- ⚠️ **`load` 本身不在此列**：它就是"初始化"这个动作，⛔ 别把它也当成"静默无效"而绕开。
- ⚠️ 这里只写**前端这一半**；后端要不要做幂等补齐、类型校验、按主键匹配，**超出本 skill 边界**，
  按各自工程约定办。
- **反模式与替代**：反模式 ＝ `store.load(); store.addEdit(...)`（同步写法，落空）；
  替代 ＝ 把 `addEdit` 放进 `load` 的 `callback`。

**Q：审核页默认条件是「待审批」，一打开却把已审批的也全查出来了？**
A：**页面主 grid 的 store 用了 `autoLoad:"true"`**。`autoLoad` 的初始化加载**不经过查询条件面板**
⇒ 即使页面赋了默认查询条件，也不会被带上 ⇒ 默认筛选形同虚设。
- **规范**：**所有页面的主 grid 一律 `autoLoad:"false"`**；需要首屏就查 ⇒
  在加载逻辑里**先赋默认查询条件、再代码触发「查询」按钮的点击事件**（⛔ 别靠 `autoLoad` 代替点击）。
- ⚠️ **触发条件不是「有没有 `panelCondition`」** —— 查询条可能只是一条 `toolbar`，没有 panel 照样中招。
- ⚠️ 刷新 / 查询写 `store.load({out: …})` 时，`out` 必须指向**实际的查询条件载体**
  （`panelCondition`，或那条 `toolbar` 的 `itemId`），⛔ **写死 `app.panelCondition`** ——
  查询条不是 panel 的页面会取到"没有这个控件"。
- ⚠️ **别和上一条混**：上一条是「**没 `load` 过** ⇒ 加行不生效」，本条是「**自动 `load`** ⇒ 绕过查询条件」，
  两者**方向相反**。
- **反模式与替代**：反模式 ＝ 主 grid `autoLoad:"true"` ＋ 页面设默认条件（以为会自动带上）；
  替代 ＝ `autoLoad:"false"` ＋ 加载时先赋条件、再触发查询按钮的点击事件。
- `check` 对**主 grid 的 `store.autoLoad`** 会打一条 `[note]`（不进退出码）；**主 grid 的认法**（顺序即优先级）：
  ① `viewport` 下第一个 `grid` → ② 否则第一个 `tab` **之内**第一个 `grid` → ③ 都没有 ⇒ 判不出，
  此时会明确说「主 grid 未识别，请人工确认」（⛔ 不静默、⛔ 不判红；文件里一个 `grid` 都没有则不打）。
  ⚠️ 只看主 grid 的**直接子** `store`（多个时任一 `autoLoad` 即命中）；`store` 不在直接子节点上 ⇒ 同样打「未识别」。

**Q：子表的「添加」按钮到底该不该判断主表有没有保存？**
A：**没有通则，看「主表保存能不能带子表」分两支** —— 这一步决定关联 ID 从哪来、要不要拦。

| 主表保存能否带子表 | 子表「添加」要不要判主表 ID | 关联 ID 从哪来 |
|---|---|---|
| **能带**（主表保存方法已把子表列进去） | **不判** —— 拦了就走不下去（新增主表阶段本来还没有主表 ID） | **后台**取：新主表用新生成的 ID，已存在则用已有的；⛔ 前端传 |
| **不能带**（主表保存只写主表） | **要判**，提示「请先保存主表信息」 | **前端**取，添加时**赋默认值**（如 `Wb.addEdit(..., {关联字段: 主表ID}, ...)`） |

- ⚠️ **「带不带子表」本身是业务决定，⛔ 平台规定**：有的页面因为子表有"必须 N 行"这类完整性要求，
  才必须在主表保存时一起存；别的页面完全可以只存主表。
- **反模式与替代**：反模式 ＝ 不管主表怎么存，子表「添加」一律先拦「请先保存主表」；
  替代 ＝ 先确认主表保存方法带不带子表，再按上表选一支。

## 四、命令行为

工具本身的耗时、降级、退出码与新文件骨架。

**Q：新建的页面硬盘上有，但设计器左侧树里看不到？**
A：`folder.json`（设计器导航树的目录索引）没登记 —— **不登记就看不到**。
`xwl.py folders <file>` 查、`--register` 登记（默认只读）。`--register` **只认文件路径**
（给目录会被拒绝：一个目录里可能有好几个文件）；所在目录还没有 `folder.json` 时**不替你创建**
（会报错退出 2）。详见 [`SKILL.md`](../SKILL.md) 第三章第 0 步。

⚠️ **子目录是另一回事**（同一条症状，两种成因，别只查父目录）：
**子目录要手工建该目录自己的 `folder.json`**，并在**父目录**的 `index` 里加一行**目录名**
（⚠️ **不带 `.xwl`** —— 那一行登记的是**子目录**，不是文件）。
只把文件写进子目录、父目录 `index` 里没这一行 ⇒ 整个子目录在设计器里都进不了树。
- **判据**：`xwl.py folders <子目录或文件>` 会同时报"子目录未在父目录 `index` 里"与"子目录自己没有 `folder.json`"两类。
- **反模式与替代**：反模式 ＝ 在父目录 `index` 里写 `xxx/子目录/page.xwl`（把文件路径当目录项）；
  替代 ＝ 父目录 `index` 只写 `xxx/子目录`，子目录自己再建 `folder.json` 登记其中的文件。

**Q：SQL 抽出来灌进数据库报 `1064` 语法错？**
A：多半是把 `\"` 残留成了字面 `\"`。**别用「反斜杠+换行 → 换行」这种朴素替换** ——
要按加载器规则解析后再取值（`xwl.py sql` 已正确处理）。

**Q：`node --check` 说事件 JS 有语法错，但我看着没问题？**
A：`events.tagEvents` 的值是 **JSON 对象字面量字符串**（形如 `{"beforeedit": function(e){…}}`），
不是语句。`node --check` 在"语句位置"看到以 `{` 开头的代码会当成块语句 → **误报**。
工具已包一层括号复验；自己写脚本时要记得。

**Q：`expand` 跑完文件没变化，是没生效吗？**
A：可能是它本来就已经是设计器排版。**不是所有 xwl 都由设计器写过** ——
手工改过的文件缩进可能是 4 空格 + 行尾空格。判断是否"设计器原样"别用眼睛看，
用 `expand --dry-run` 比字节。该用忠实模式还是 `--safe` 见 [`measured-data-designer.md`](measured-data-designer.md) §5.2。

另有一种"变化很小但换行变了"的情况：**源文件是紧凑一行、末尾也没有换行符**时，
`--eol auto` 无从"沿用"，会**回退 LF**。这条回退规则 `patch` / `edit` / `expand`
**三命令共用**，且**不静默**（各命令都会在输出里写明选了哪个换行）。这类文件（样本工程 902 个）跑完就变成 LF 文件 ——
工作区惯例是 CRLF 的话请显式 `--eol crlf`。输出里 `规范化后: … 换行=LF` 会写明它选了哪个。

**同一条回退规则 `patch` 也有**：它对无换行的单行源同样回退 LF，并在头部那行直接注明
`换行=LF（源无换行符，auto 回退 LF）`。另外 `patch` **整份重建**，所以改单行源的结果一定是多行
（diff = 整个文件），它会带 `[warn]` 说明 —— 要把 diff 压小就改用 `edit`。

**Q：`check` 慢，或者本机根本没装 `node`？**
A：⑥ 的事件 JS 校验需要 `node`；找不到时**自动降级为提示**（不阻塞，退出码照常）。
- 只想确认"文件本身没坏" → `check --no-js` 就够，它不碰 node；
- 只想验命名质量 → `check --no-js` 仍会跑 ⑦ 注册键重名分级。

被跳过的 ⑥ / ⑦ 会在输出里以 `[note] … 已跳过` 明确标注，**不会静默消失** ——
所以任何时候你都能从输出确认"九项里哪几项真跑了"。

**耗时构成**（实测 486 KB 多行源 / 246 个事件段；另在**实测最大的 728.8 KB**（746299 字节）文件上复测：
`check --no-js` **0.08 s** / `check` 全开 **0.56 s** / `params` 0.05 s / `itemids` 0.07 s ⇒ 性能不是约束）：

下表是**上面那个 486 KB 样本**上的分项构成（728.8 KB 的总量见上一行）：

| 命令 | 耗时 | 说明 |
|---|---|---|
| `check --no-js --no-itemid` | ~0.4 s | 只跑格式五项 |
| `check --no-js` | ~0.4 s | 加上 ⑦ 注册键重名分级 |
| `check`（全开） | **~1 s** | ⑥ 会把**全部事件段一次**交给 node 校验 |

⇒ **格式检查（①–⑤）与 ⑥ 的成本差异很大**：只想确认"文件本身没坏"就先跑 `check --no-js`；
需要 JS 语法校验时再跑全量。规模再大（MB 级）时 ⑥ 的占比会继续上升。

**Q：`new` 生成的骨架里，`module` 和 `dataprovider` 的 `itemId` 就叫这俩名字吗？改了行不行？**
A：就叫 `module` / `dataprovider`，所以 `@module` / `@dataprovider` 可以直接寻址。
改名可以，但**多个 SQL 载体放在同一个文件里时才会冲突** —— 那种情况要自己区分开，
并用 `xwl.py paths` 确认 `@` 名字唯一（重名时工具会拒绝执行并给候选清单）。

**Q：脚本 / CI 里怎么判断命令成功没成功？**
A：**看退出码，不要 grep 输出文本** —— `[warn]` 是有意设计成不阻塞的（**不影响退出码**）
（老代码里的无害重名，见 [`SKILL.md`](../SKILL.md) 第七章）；
退出码本身也不是"1 与 2 严格二分"（同为"文件不存在"，`check` 给 1、`patch` 给 2）。

判成功除了看退出码，还要把**输出约定**读对：
**行首标记**共四值 —— `[ok]` / `[FAIL]` / `[warn]`（**不影响退出码**）/ `[note]`；
**带结论的三个命令**（`check` / `sqlrefs` / `diffguard`）给**两级**结论 —— 单个文件的结论是逐项的
`-> OK` / `-> FAIL`（两格缩进），整个命令的末行是 `=== 结果: ALL OK` / `=== 结果: FAIL`
（`sqlrefs` 还有 `=== 结果: OK（有警告）`）。
其余是**报告类**命令（`itemids` / `folders` / `paths` / `params`），**没有这种末行** —— 判成败请认退出码。
三个码各代表什么见 [`SKILL.md`](../SKILL.md) §4.2。

**若消费 `itemids <file> --json`**：`groups[].name` 的值 = **注册键 `normalName || itemId`**（**不是 `itemId`**）；
`groups[]` 另有 `itemIds`（该组节点的 `itemId` 列表）与 `registryName`；`--name --json` 的每个 node 项含 `itemId`。
字段名不变、但 `name` 的**值**按注册键走 —— 汇总请用 `itemIds` / `registryName`，照 `name == itemId` 写的脚本要改。

**Q：`patch` 明明显示 `ALL OK`，紧接着跑 `check` 却报 `[FAIL] ⑩ configs 值类型`？**

A：**这是有意的分工，不是漏判**。`patch` 写盘后的自动校验**只判 ①–⑥**、**故意不判 ⑩** ——
⑩ 判的是**文件既有**的内容属性（写盘只搬字节、不改值），若在写盘路径上判，会让**本来能写盘**的存量坏文件突然 `patch` 失败（行为突变）。
所以要么 `patch` 报错、要么 `check` 报红，二者只能取一个；工具取"写盘不挡、`check` 判红"。

⚠️ 但这不等于"事后才知道"：**本次写入的对象**若含非字符串的 `configs` 值，`patch` / `edit` / `expand` / `new`
的 `--- 自动校验（本次改动是否破坏格式）---` 段里会多打一行（**`rc` 仍是 0、值不会被自动改**）：

```text
[warn] 本次写入含 1 处 configs 非字符串值（t1.width）：check 的 ⑩ 会判 FAIL，请改成字符串
```

- 列名最多列 **8** 个（`<itemId>.<key>`），超出以 `…` 结尾、`N 处` 给总数；`configs` 全为字符串时**这行不打**（正常文件输出不变）。
- **看到这行就要回去改值**（`"width": "40"` 而不是 `40`），别等 `check`。
- ⛔ 它不是错误：`patch` 该给的 `rc=0` 照给（所以**别写成"patch 会报错"**）；`--dry-run` 也不打这行（没写盘）。
