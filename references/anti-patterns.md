# 反模式：看起来对、实际有害的做法

**这份文档是「动手前」看的。** 它与 [`faq.md`](faq.md) 互补 ——
FAQ 回答"**已经坏了怎么救**"（按症状查），这里回答"**你正打算做的事为什么是坑**"（动手前扫）。

判据是**能不能静默通过**。本工具的质量保证是"格式错误在构造上不会发生"，代价是
**多数错误不报错**：下表标「静默」的那些，`check` 全部放行，只能靠**相对基线的复核**发现
（人工 `git diff`，或见下方那条例外）。所以这份清单不是补充材料，
它覆盖的正是本工具最容易出事的那一面。

> 唯一有**自动化防线**的是第 4 条（压成一行）：`xwl.py diffguard` 能相对 git 基线把它揪出来。
> 其余"静默"项仍然只能靠人工复核（`git diff`）。

> 文中的 `SKILL.md` 均指 [`../SKILL.md`](../SKILL.md)；`xwl.py` 指 [`../scripts/xwl.py`](../scripts/xwl.py)。

## 一、碰文本层

### 1 · 用普通编辑器 / 通用 Edit 工具直接改 .xwl

- **错误做法**：打开文件，改掉那一小段，保存。
- **为什么诱人**：只改一个字符，编辑器是最快的路径；而且看起来"反正内容不变"。
- **实际后果**：**写成裸 LF** —— 磁盘形态本该是「字面反斜杠 + 真实换行」，普通编辑器会把它改成
  真换行，运行时解析失败、页面白屏。这类改动**没有任何工具会拦你**。
- **正确做法**：默认走 `patch`（只提供值/子树，格式由序列化器产出）；
  确需定点文本替换时用 `edit` —— 它**按目标文件的换行**归一锚点、**断言锚点出现次数**，
  且**把多行拍平时会主动给 `[warn]`**（第 2 条那种静默损坏，只有这一处能提示）。

### 2 · 用文本替换批量改一批 .xwl

- **错误做法**：写个脚本，对几十个文件跑同一个替换。
- **为什么诱人**：比一个个 `patch` 快得多，尤其"改个字段名"这种看起来机械的活。
- **实际后果**：两层损坏 —— ① 格式同第 1 条一样被破坏；② 全文相同的锚点
  （`select`、相同按钮文案、相同 `itemId`）会被**一起改掉**，而改错的地方不会报错。
- **正确做法**：一个个走 `patch`。锚点不唯一时把锚点**扩到足够上下文**直到唯一，
  **不要**用 `--expect N` 放行（见第 11 条）。

### 3 · 手工统一换行符

- **错误做法**：把文件里的换行全改成 CRLF（或全改成 LF）。
- **为什么诱人**："既然要求全文件一致，那统一一下更规范"。
- **实际后果**：与 git 的 `core.autocrlf` 打架，**整份文件都变成 diff 噪音**，
  这次真正的改动被淹没，评审时看不出来。
- **正确做法**：**不要手工改**。规则只是"同一文件内不混用"——
  LF-only 与 CRLF-only **都合法**（加载器两种都收）。

## 二、关于"压成一行"

### 4 · 把多行源压成一行

- **错误做法**：把「反斜杠 + 换行」直接删掉，让长字符串合并成一行。
- **为什么诱人**：想省体积、方便传输，或者单纯觉得紧凑"更好看"。
- **实际后果**：**静默语义损坏**，而且是最危险的一类 ——
  删除后文件**依然是合法 JSON**；`//` 行注释会把后面的代码**整段吃掉**
  （这类结果 `node --check` 还会**返回 0**，因为"只剩一句注释"本身是合法 JS）；
  `return` / `throw` / `++` / `--` 后面的换行一旦消失，ASI 语义就变了；
  SQL 侧 token 会粘连（`select 1from dual`）。
  **格式校验、语法校验全部放行。**
- **正确做法**：多行源**绝不能**压成一行 —— 这条**没有例外**（要单行形态只在单行源上做）。
  而且**改完就跑一次 `xwl.py diffguard`** —— 它的主判据是定义级的
  （工作区某行 == 基线连续多行去掉续行符后拼接），"合法删减"与"单行改长"都不会误报；
  这是**唯一**能自动发现这类损坏的手段（`check` 与 `node --check` 都放行）。
  详见 [`../SKILL.md`](../SKILL.md) 2.3。

### 5 · 用严格 JSON 解析器判断"能不能加载"

- **错误做法**：拿 `json.loads` 试一下，抛异常就说明文件坏了。
- **为什么诱人**：手边就有，一行代码。
- **实际后果**：加载器用的是 **org.json，比标准 JSON 宽容** ——
  字符串里出现未转义的裸控制字符（如裸换行）它照收。
  于是**合法文件被判成坏文件**，你会去"修"一个本来没坏的文件。
- **正确做法**：用 `check` 的 ④（加载器等价解析）。
  自己实现的话，先把「反斜杠 + 换行」替换成**「反斜杠 + 字母 n」两个字符**再解析 ——
  注意不是替换成换行符，写错会误报。

### 6 · 只看 `check` 全绿就交活

- **错误做法**：改完跑 `check`，全绿就认为改对了。
- **为什么诱人**：工具都说 OK 了，还能有什么问题。
- **实际后果**：`check` 只证"**格式**能加载"，**查不出语义变化** ——
  JS 逻辑改了、SQL 条件从 `=` 变成 `like`、参数名写错，它一律看不出来。
- **正确做法**：三层缺一不可 —— ① `check` 全绿；② `git diff` 复核
  （"多行被压平"这一档可以直接跑 `xwl.py diffguard`，它自动做这件事）；
  ③ 涉及 SQL / 传参时把抽出的 SQL 灌真实库跑一遍（或交叉核对 `sqlrefs` / `params`）。

## 三、新建与骨架

### 7 · `cp` 一个别的 .xwl 当种子，再整树重写

- **错误做法**：复制一个已有的、体积最小的 xwl 当壳，用 `patch` 把 `children` 整树换掉。
- **为什么诱人**："内容反正会被覆盖，越小残留越少"。**这个直觉是错的。**
- **实际后果**：种子是**继承式**的 —— 顶层**没被显式 `set` 的键会静默残留**
  （种子的 `roles:{"demo":1}` 会跟着进新页面，把 demo 角色权限带进去）。
  若种子本身是「缺钥匙」的文件（工程里确实存在），产出会**少 `inframe` / `pageLink`
  而 `check` 仍报 ALL OK**。
  另有一个反直觉的实测结论：两个内容毫不相干的种子套用同样的 ops，产出**逐字节相同** ⇒
  "找内容相近的种子"这件事本身没有意义。
- **正确做法**：用 `xwl.py new`（内置设计器真实键序），不需要任何种子文件。

### 8 · 手写顶层 7 把钥匙

- **错误做法**：照着 `SKILL.md` §1.3 的键序，把 7 把钥匙手敲一遍。
- **为什么诱人**：就 7 个键，看着简单。
- **实际后果**：两层静默 —— ① 漏 `inframe` / `pageLink` 时 `check` **照样 ALL OK**，
  问题被吞掉；② **键序写错**则产出与设计器不一致，下次被设计器保存就产生一批
  与本次改动无关的 diff。
- **正确做法**：用 `new`；或用 `new --from-json` 喂自己拼的顶层对象，
  它会按设计器键序**重排并补齐缺失的钥匙**，并把补齐了哪些明确回报。

### 9 · 想"把整个目录登记进 `folder.json`"

- **错误做法**：`xwl.py folders <目录> --register`，想把目录里所有文件一次登记。
- **为什么诱人**：一次搞定一个目录，比逐个文件省事。
- **实际后果**：`--register` 只认**文件路径**；给目录会被**明确拒绝**（退出码 2）——
  一个目录里可能有好几个文件，工具不知道要登记哪一个。
- **正确做法**：给具体文件路径：`xwl.py folders <目录>/<文件>.xwl --register`。
  另外该目录必须**已经被设计器管理**（已有 `folder.json`），否则会报错而**不会**替你创建。

## 四、路径与寻址

### 10 · `patch` 的 `path` 漏 `configs` 一层

- **错误做法**：按"节点底下就是字段"的直觉写 `["children",0,"serverScript"]`。
- **为什么诱人**：`serverScript` 在文档里是跟着节点一起讲的，直觉上像节点自己的字段。
- **实际后果**：`patch` **不报错**（产出格式合法），而是把字段写到**节点根**上
  （变成 `{"type":"module","serverScript":…}`），`check` 也拦不住。**静默语义损坏。**
- **正确做法**：照抄 `paths` 给出的「原路径」（它**已经带 `configs` 一层**），
  或直接用 `@itemId` 写法 `["@dataprovider","configs","sql"]`。
- **相关（新建键）**：`set` 一个**原本不存在**的对象键（如给缺 `inframe` 的页面补钥匙）属**新建键**，该 op 要带
  `"create": true` —— 与本节"漏 `configs` 层"是两回事（那是**写错地方**，这是**往不存在的键写**）。
  本版不带 `create` 也放行、只打一行 `[warn]` 预告；默认拒绝将在后续版本启用。

### 11 · 锚点不唯一时用 `--expect N` 放行

- **错误做法**：`edit` 报"锚点出现 5 次"，于是加 `--expect 5` 让它过去。
- **为什么诱人**：工具都把次数告诉我了，加个参数就能继续，看着像"确认一下"。
- **实际后果**：那 5 处会被**一起改掉**，其中 4 处可能根本不该动。
- **正确做法**：把锚点**扩到足够上下文**直到唯一。出现次数多到无法扩唯一时，
  说明这次改动不该用文本替换 —— 改走 `patch`。

### 12 · `@itemId` 重名时"猜第一个"

- **错误做法**：重名了，挑第一个改。
- **为什么诱人**：几个同名节点看着差不多，觉得"反正都是同一个东西"。
- **实际后果**：**改错对象，而且没有任何提示**。
- **正确做法**：三种精确指定 —— ① `@名字#N` 点名第 N 个（N 从 1 起）；
  ② 串联 `@` 段缩小范围（`["@gridUser","@tbar"]`，后一段只在上一段子树里找）；
  ③ 按父子关系确认后再改。工具本身**不猜顺序**、也**别猜**第一个，会给候选清单。

## 五、重名处置

### 13 · 重名时"删一个"或"随便挑一个改"

- **错误做法**：看到重名告警，删掉一个、或给任意一个改名了事。
- **为什么诱人**：想把告警消掉，看起来"清理干净了"。
- **实际后果**：可能删掉/改名了**真正被 JS 引用**的那个；
  而重名的真实故障形态是"**打开一个窗口再关掉，另一个同名控件就失效了**"这种
  偶发、难复现的取不到值 —— 因为框架注册是普通赋值、注销是**按同名键直接 `delete`**，
  任一重复项被销毁会把整个名字从页面作用域删掉。
- **正确做法**：读**祖先链**判断哪个才是真正要改的 → **把候选清单交给用户选**
  （工具只提建议）→ **优先补 `normalName`**（不动 `itemId`，零破坏）；
  只有该控件类型不接受 `normalName` 时才回退到改 `itemId`，且**必须同步改事件 JS 里的引用**。

### 14 · 给不接受 `normalName` 的控件写 `normalName`

- **错误做法**：听说"补 `normalName` 是首选"，于是给布局 / HTML / 后端节点也补上。
- **为什么诱人**：它确实是首选方案，而且看着"多加一个键总没坏处"。
- **实际后果**：`normalName` 虽是合法 configs 键，但**不是所有控件都接受** ——
  注册表 `wb/system/controls.json` 里有一部分控件的 `configs` 没有这个键，
  写进去属**非法配置**。
- **正确做法**：先查 `xwl.py schema <type> --controls <工程>/wb/system/controls.json`。
  用 `itemids --fix normalName` 时工具**会跳过并回报**（自动跳过不支持的类型）。

### 15 · 把样本工程的比例当阈值

- **错误做法**：文档里写着"列控件注册键重名 3393 组、被引用的 0 组"，于是在自己工程里也照此判断。
- **为什么诱人**：有现成数字，省得自己统计。
- **实际后果**：那只是**一个样本**的量级参考，不是规范。换工程、换命名习惯，结论可能完全不同。
- **正确做法**：在**自己的工程**上跑一遍 —— `itemids` 给分级与候选、`check` 的 ⑦ 给计数。

## 六、SQL 与传参

### 16 · 在 `serverScript` 里写 `{#…#}`

- **错误做法**：`dataprovider.sql` 里用 `{#sql#}` 取值，于是 `serverScript` 里也照着写。
- **为什么诱人**：看着一致，像是同一套占位符。
- **实际后果**：加载器**明确报错**（有源码原文）：
  `ServerScript does not support {#param#} feature, please use app.get(param) instead.`
- **正确做法**：`serverScript` 内部取参数一律用 `app.get('名字')`。
  `{#名字#}` 只属于 `dataprovider.sql`，它的源头是 `request.setAttribute('名字', …)`。

### 17 · 参数名与控件 `itemId` 不一致

- **错误做法**：SQL 里写 `{?bizNo?}`，控件 `itemId` 却叫 `orderNo` —— 或者干脆自己起个更"业务"的名字。
- **为什么诱人**：参数名看起来是"自己起"的，业务名字更可读。
- **实际后果**：**不报错**，取到 null，**SQL 条件静默失效** ——
  查询结果不对，但没有任何报错指向这里。
- **正确做法**：参数名 = 控件的 `itemId`，**一路同名**到 `{?名字?}`。
  改完跑 `xwl.py params` 看有没有「SQL 需要但页面未发现来源」的告警。
  新写查询推荐用 `out` 通路（`params` 也可以，规则见 SKILL.md 第五章）。

### 18 · 用 `Wb.request` 代替 `store`

- **错误做法**：列表数据也用 `Wb.request` 去请求 SQL 片段。
- **为什么诱人**：`Wb.request` 的写法更直观，和平时请求后台片段一致。
- **实际后果**：**分页 / 排序失效** —— 框架不会替你带 `page` / `start` / `limit`，
  也不处理返回结构。
- **正确做法**：列表、分页、排序用 `store.load(...)`（配合 `store.configs.url`）；
  `Wb.request` 留给"不建页面、只要结果"的查询 / 校验 / 取数。

### 19 · 手工拼 SQL 值

- **错误做法**：把参数值直接拼进 SQL 字符串。
- **为什么诱人**：字符串拼接最直接，不用理解占位符机制。
- **实际后果**：得自己操心转义，还要面对注入问题。
- **正确做法**：`{?名字?}` 是**绑定参数**（`PreparedStatement`），**不是文本替换** ——
  用它就不需要拼值。
  （`{#sys.*#}` / `{#Str.*#}` 是框架内置的会话 / 权限注入，不用自己提供。）

## 七、产物形态

### 20 · 给要提交的文件用 `expand --safe`

- **错误做法**：为了"看着舒服"，把生产文件用 `expand --safe` 转一遍。
- **为什么诱人**：`\\n` 比「反斜杠 + 换行」直观，人读起来不费劲。
- **实际后果**：产出**与设计器产物不一致**，下次设计器一保存就冒出一堆
  与本次改动无关的 diff，真正的改动被淹没。
- **正确做法**：按"**这个文件给谁看**"决定，别按"哪个好看"决定 ——
  要提交 / 要给设计器继续编辑 / 要上生产 → 用默认**忠实模式**；
  只想人读一遍 → 用 `--safe`，或者干脆用 `xwl.py sql` / `xwl.py events`
  把内容抽出来读（连文件都不用动）。

### 21 · 给 `patch` / `expand` 传 `--indent`（非 1）

- **错误做法**：`xwl.py patch page.xwl --ops ops.json --indent 4`（想着"4 空格比 1 空格好看"）。
- **为什么诱人**：它在 `--help` 和工具表里明明白白列着，看着是个正常的排版选项。
- **实际后果**：**产出与设计器不一致** —— 设计器写回固定是 1 个空格缩进
  （`json.toString(1)`，见 [`faq.md`](faq.md) §四）。于是下次设计器一保存，
  整份文件被重排，冒出与本次改动无关的**大量** diff；再用默认参数跑一次 `patch`，
  又会整份重排回去（实测 `--indent 4` 产 643 B、改回默认 −147 B，两次都是全文件 diff）。
  更麻烦的是：**这是唯一一个能主动击穿"diff 只含本次改动"这条核心保证的入口**。
- **正确做法**：**别传它**（现在非 1 会给 `[warn]`，就是为提醒这一点）。
  它存在的意义是**排版复刻实验** —— 验证序列化器与设计器算法一致时用来对照，
  不是日常编辑的选项。

### 22 · 拿实例当配置：`new Ext.window.Window(app.X)`

- **错误做法**：把窗口控件**当配置对象**反复喂给构造函数 —— 每次打开都 `new Ext.window.Window(app.X)`。
- **为什么诱人**：`app.X` 在页面作用域里总能拿到，看着就是那个窗口的配置。
- **实际后果**：`app.X` 是**实例句柄**（框架在生成期已 `new` 过一次）⇒ 等于拿实例当配置：
  `closeAction` 为 `destroy` 时，控件销毁会把 `app.X` 从作用域里删掉 ⇒ **第二次打开是空白窗**；
  为 `hide` 时能显示，但会**留下一个泄漏的旧实例、并可能重复 id**。`check` 全绿放行（静默）。
- **正确做法**：**每次重建**用 `app._X`（配置模板键、永不被注销）作构造参数：
  `new Ext.window.Window(app._X)`（配 `createInstance:"false"` + `closeAction:"destroy"`）；
  **常驻**则根本不 `new`，只 `app.X.show()` / `app.X.hide()`。判别与正反例见 `js-api.md` §5。

### 23 · 窗口写法与 `closeAction` 不配套

- **错误做法**：`closeAction` 留缺省却每次 `new`；或声明 `destroy` 却仍按常驻写法反复 `app.X.show()`。
- **为什么诱人**：两种写法单看都"能跑"，配套关系是隐式的，容易只改一半。
- **实际后果**：留缺省（= `hide`）却每次 `new` ⇒ 旧的隐藏实例**不被销毁、越开越多**；
  声明 `destroy` 却复用 `app.X` ⇒ 销毁后再取 `app.X` 是 `undefined`、得到空白窗。同样**静默通过 `check`**。
- **正确做法**：把"打开 / 关闭 / `closeAction`"当成**一组**一起写 —— 常驻（`hide` + `app.X.hide()`）
  或每次重建（`createInstance:"false"` + `app._X` + `closeAction:"destroy"`）；窗口要重建还需挂到
  `module` 直接子级才拿得到 `app._X`。完整对照见 `js-api.md` §5，实测分布见 `measured-data.md` §十二。

## 只记三条的话

上面 23 条里，如果只记三条：

1. **别碰文本层** —— 文本替换、编辑器直改、批量替换都会破坏格式，而**没人会拦你**。
2. **别压成一行** —— 多行源压行是静默语义损坏，`check` 与 `node --check` 都放行，
   只有 `diffguard` 或人工 `git diff` 能发现（`diffguard` 是它的自动化形式）。
3. **别把"check 全绿"当改对了** —— 它只证格式能加载，语义层要另做验证。
